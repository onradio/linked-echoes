# Entity linking evaluation — methodology and results

_Generated by `report.py` from `data/results/`. Do not edit: re-run `score.py && report.py` instead._

## Methodology

**Benchmark.** BME-EL, derived from 115 distinct mentions over 65 catalogued objects of the *Beyond the Music* collection, covering ten entity types. A mention is a distinct (normalised label, entity type) pair; surface errors in the legacy records are preserved rather than corrected, because resolving them is part of the task. 112 mentions are scored; 3 are excluded as `data_error` (legacy column shifts that are not entities).

**Gold standard.** A single annotator resolved every mention against Wikidata directly rather than against the systems' candidate lists, so the gold is independent of what retrieval found and retrieval misses remain measurable. Where more than one item is defensible the alternates are recorded and scoring accepts any of them. Mentions with no correct Wikidata item are labelled NIL and **are** scored: correct abstention is a result, not a nuisance.

**Frozen candidate pools.** Wikidata's search ranking drifts, so the top-50 candidates per mention were retrieved once and pinned (11 types; mean pool depth 23.4, median 17). Every depth $k$ is a slice of this list, never a re-query, and each candidate's `P31` classes are stored alongside it.

**Type checks (ECKs).** One SPARQL `ASK` per entity type, evaluated against the frozen pool and cached. The checks were developed and unit-tested against an independent fixture of 158 assertions over 111 Wikidata entities and frozen as `v1` *before* the pools were retrieved, so they are not fitted to the evaluation set. A query that cannot be evaluated is recorded as `error_api` and never as a rejection.

**Systems.** All four consume the same frozen pool truncated to $k$, and all LLM-based systems receive an identical prompt that already states the expected type — the comparison therefore isolates *hard* type enforcement, not the presence of type information.

| Id | Pipeline |
| --- | --- |
| `S0` | candidate at rank 1; never abstains |
| `S1` | highest-ranked ECK-valid candidate; abstain if none |
| `S2` | LLM selects from the unfiltered top-$k$; may abstain |
| `S3` | ECK filter, then LLM selects; may abstain |

**Protocol.** $k \in \{5, 10, 25, 50\}$, headline $k=10$; three runs per cell at temperature 0 for the LLM systems (`S0` and `S1` are deterministic). Significance is McNemar's exact test on the paired decisions; 95% intervals are a cluster bootstrap over objects (10000 resamples), since mentions on the same object share disambiguating context.

## Results

**Symbolic validation beats soft type conditioning (C1).** At $k=10$, accuracy rises from 0.827 for the unvalidated neural system to 0.935 for the neuro-symbolic one (Δ +0.107, 95% CI [0.052, 0.164]), with both systems given the same type information in the prompt. McNemar's exact test on the paired decisions gives $p = 0.0018$ with discordant counts $b = 1$ / $c = 13$. Link precision — the metric that matters when a wrong link writes a false statement into the knowledge graph — rises from 0.831 to 0.946.

The mechanism is visible in the error attribution: spurious links (asserting an entity where the gold is NIL) fall from 13 to 4, and wrong links from 4 to 1. Validation converts confident wrong answers into abstentions, which a curator can act on.

**Robustness to distractor pressure (C2).** As retrieval widens from $k=5$ to $k=50$ the unvalidated system degrades (0.863 → 0.824) while the validated one stays essentially flat (0.943 → 0.929) and leads at every depth. Validation therefore lets an institution widen retrieval — raising the chance the right entity is present at all — without paying for it in precision. Mean pruning at $k=10$ is 6.8 → 1.5 candidates.

**Where the benefit lands (C3).** The gain is concentrated in the types where surface strings are ambiguous:

- **music work** (23 mentions): 0.594 → 0.942 (+0.348)
- **country** (5 mentions): 0.800 → 1.000 (+0.200)
- **venue** (8 mentions): 0.625 → 0.750 (+0.125)
- **music genre** (9 mentions): 0.889 → 1.000 (+0.111)

Types whose names are near-unique — colour, material, event — are already saturated and gain nothing, which is the expected shape.

**The symbolic step costs nothing measurable.** The validator false-rejection rate — gold entities retrieved but rejected by their own check — is 0.00 overall and in every individual type. Retrieval recall at $k=10$ is 0.99, so the filter is not discarding correct answers; it is discarding wrong ones.

**The filter carries most of the weight.** `S1`, which applies the checks and takes the highest-ranked survivor with no language model at all, reaches 0.893 — above `S2` at every depth and at no inference cost. The generative step adds precision on top (0.889 → 0.946) rather than doing the bulk of the disambiguation.

## Limitations

- **Single annotator.** No inter-annotator agreement is reported; the guidelines and full gold set are released so the labels can be audited.
- **Small per-type samples.** Event (2 distinct mentions) and venue (8) cannot support a claim on their own and are reported as indicative. Works (23) and albums (10) are the defensible part of C3.
- **Pool saturation dilutes the depth sweep.** 36% of mentions return fewer than five candidates, so their pool is identical at every $k$ and they flatten both curves; the effect in the figure is a lower bound.
- **Gold treats a release as not a work.** Where Wikidata holds only the single and not the composition, the mention is annotated NIL. This is a schema-integrity decision — linking a single into a work slot writes a false statement — taken before any system was run, but it does favour systems that can abstain, and the effect is concentrated in the music-work type.
- **Only the Wikidata path is evaluated.** The DBpedia templates are retained for API compatibility and are not exercised.
